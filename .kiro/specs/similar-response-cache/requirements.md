# Quick Spec — Similar Response Cache (`cache: similar`)

Тип: **Quick Spec** (фича 1-3 дня; requirements + tasks, дизайн кратко).
Requirements здесь, задачи в [tasks.md](tasks.md).

## Контекст / проблема

`internal/cache/cache.go:293` содержит `FindSimilar(model, body, threshold)` —
дешёвый near-duplicate lookup по Jaccard на словах последнего сообщения `user`,
без эмбеддингов. Он написан, покрыт юнит-тестами и **не вызывается ниоткуда,
кроме тестов**: шлюз ходит только в `Get(KeyFor(model, body))`
(`internal/proxy/proxy.go:437-438`), то есть точное совпадение байтов. Запись
данных для похожего поиска при этом уже работает — `proxy.go:561` вызывает
`SetWithRequest(..., body, ...)`, и `RequestHash`/`RequestWords` заполняются
(`cache.go:206-207`). Не хватает только чтения.

Прежде чем это включать, в самой функции есть три дефекта, которые в мёртвом
коде не проявлялись:

- **H1 — параметр `model` не используется.** `FindSimilar` перебирает все записи
  `c.entries` и сравнивает только хэш и слова, хотя ключ построен как
  `KeyFor(model, body)`. Похожий вопрос, закэшированный для `gpt-5`, будет отдан
  запросу к `claude-opus-4-5`.
- **H2 — сходство считается по последнему сообщению `user`, и только по нему**
  (`requestUserWordList`). В агентском цикле последнее сообщение user часто
  короткое и повторяющееся («continue», «fix the failing test»), а история
  различается полностью — Jaccard даст 1.0 и шлюз отдаст ответ на другую задачу.
  Порог 0.8 на сообщении из трёх слов удовлетворяется двумя общими словами
  (`wordList` отбрасывает слова длиной <=2).
- **H3 — двойной учёт статистики.** `FindSimilar` сам зовёт `noteHit(true)` /
  `noteMiss()`, хотя как вторичный lookup он вызывается после `Get`, который
  промах уже записал.

## Функциональные требования

### FR-1: Третий режим кэша `similar`
- `config.Model.Cache` SHALL принимать `similar` наряду с `off` и `exact`;
  валидация `internal/config/config.go:535` расширяется, сообщение об ошибке тоже.
- `cache_similar_threshold` (float, по умолчанию **0.95**) SHALL задаваться на
  модель; вне диапазона (0, 1] — ошибка конфигурации.
- WHEN `cache: similar`, THEN шлюз SHALL сначала пробовать точное совпадение, и
  только на промахе — похожее.
- Приоритет: MUST
- **AC-1.1**: `cache: exact` ведёт себя ровно как сейчас (регрессия).
- **AC-1.2**: конфиг с `cache: similar` и порогом 1.5 не стартует с внятной ошибкой.

### FR-2: Изоляция по модели
- Похожий поиск SHALL рассматривать только записи той же модели.
- Приоритет: MUST
- **AC-2.1**: запись, положенная для `model-a`, никогда не отдаётся запросу к `model-b`,
  даже при полном совпадении текста.

### FR-3: Область применения — только одношаговые запросы
- Похожий поиск SHALL применяться, только если запрос выглядит одношаговым:
  нет поля `tools`, нет сообщений с ролью `tool`, и не более двух сообщений
  помимо `system`.
- Значимых слов в последнем сообщении `user` SHALL быть не менее **8**;
  иначе похожий поиск не выполняется.
- Приоритет: MUST
- **AC-3.1**: агентский запрос (есть `tools` либо `role: tool`) никогда не получает
  похожий хит, даже при идентичном последнем сообщении user.
- **AC-3.2**: короткий запрос («continue») никогда не получает похожий хит.

### FR-4: Наблюдаемость похожего хита
- WHEN отдан похожий хит, THEN ответ SHALL несёт `X-Gateway-Cache: HIT-SIMILAR`
  и `X-Gateway-Cache-Score` с фактическим Jaccard, а телеметрия — outcome
  `cache_similar`.
- Приоритет: MUST
- **AC-4.1**: точный хит по-прежнему помечается `HIT`; похожий отличим от него.

### FR-5: Учёт статистики без двойного счёта
- `FindSimilar` SHALL NOT вести собственный учёт hit/miss; учёт остаётся за
  вызывающей стороной, как для `Get`.
- Приоритет: MUST
- **AC-5.1**: одна серия «промах точного, хит похожего» даёт ровно один hit и
  ноль лишних miss в `/api/cache/stats`.

### FR-6: Приоритет отказа клиента
- `X-Gateway-Cache: false` SHALL отключать и точный, и похожий поиск.
- Стриминг и `X-Gateway-Output-Format: anthropic` SHALL остаться исключёнными
  (существующее условие `proxy.go:427`).
- Приоритет: MUST
- **AC-6.1**: с `X-Gateway-Cache: false` заголовков кэша в ответе нет.

## Нефункциональные требования

- **NFR-1**: похожий поиск — линейный перебор под `RLock`; при `maxSize` записей
  он SHALL добавлять не более 1 ms на промахе точного кэша. Замер обязателен, не
  предполагается.
- **NFR-2**: никаких эмбеддингов и новых зависимостей; Jaccard остаётся as-is.
- **NFR-3**: режим по умолчанию не меняется — `similar` включается только явно.

## Дизайн (кратко)

- `FindSimilar` получает фильтр по модели: ключ уже содержит модель
  (`KeyFor`), поэтому достаточно сравнивать префикс ключа с `KeyFor(model, nil)`-
  эквивалентом, либо (предпочтительно) хранить `Model` в `Entry` при записи и
  сравнивать поле. Второе явнее и не зависит от формата ключа.
- Гейт одношаговости (`FR-3`) считается один раз на запрос в `internal/cache`
  (рядом с `requestUserWordList`, чтобы разбор тела не дублировался) и
  возвращает `eligible bool` вместе со списком слов.
- В `proxy.go` похожий поиск встаёт в существующий блок `if wantCache`, сразу
  после промаха `Get`; путь записи не меняется.
- Порог и режим наследуются как остальные squoze/cache-поля: virtual > model > global.

## Edge cases

- Мультимодальный контент (`content` массивом) — `requestUserWordList` вернёт
  nil, похожий поиск не выполняется (fail-closed, поведение сохранить).
- Запись без `RequestWords` (положена через `Set`, а не `SetWithRequest`) —
  в переборе пропускается.
- Два кандидата с одинаковым Jaccard — детерминированный тайбрейк по ключу,
  чтобы ответ не зависел от порядка обхода map.
- TTL истёк у лучшего кандидата — он не рассматривается (существующая проверка).

## Ограничения

- Семантический кэш на эмбеддингах остаётся Cloud/Ent и этой спекой не трогается.
- Похожий хит — это ответ на **другой** запрос. Поэтому режим не может стать
  значением по умолчанию ни для одной модели.
