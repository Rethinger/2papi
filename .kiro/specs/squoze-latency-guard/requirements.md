# Requirements — Squoze Work Guard & Envelope Reach

Спека покрывает P1 из согласованного плана: squoze должен **тратить CPU только там,
где он что-то экономит**, и доставать до тех форм данных, которые реально приходят
от агентских тулов. Обе части выходят одним релизом squoze **v0.4.0**.

Смежные: `squoze/.kiro/specs/distill-contracts/` (закрыт релизом v0.3.0, тот же
файл `json_tabular.go`) · [benchmark-integrity](../benchmark-integrity/requirements.md)
(FR-7/FR-9 — числа и README).

## Контекст / проблема

Замеры на пине **v0.3.0**, `golang:1.22` в Docker, 2026-09-05. Корпус —
синтетические агентские сессии (60 турнов по 7 000 B на блок), прогон через
`squoze.Engine.Apply`:

| Полезная нагрузка | Экономия | Apply | Блоков |
|---|---|---|---|
| JSON tool_result, блобы **байт-идентичные** | 96.4% | 11.5 ms | 59 |
| JSON tool_result, блобы **различные** | **0.0%** | **26.1 ms** | 0 |
| Проза, различная | 0.0% | 12.6 ms | 0 |
| Код, различный | 0.0% | 10.7 ms | 0 |
| Логи, различные | 0.0% | 13.9 ms | 0 |
| Один блоб 420 KB, JSON | 0.0% | 23.6 ms | 0 |
| 300 турнов, проза (2.1 MB) | 0.0% | 61.5 ms | 0 |
| 300 турнов, код (2.4 MB) | 0.0% | 53.8 ms | 0 |

Отсюда два независимых дефекта.

**Д1 — работа без отдачи.** Заявленные 95% экономии дают не дистилляторы, а
кросс-турновая дедупликация байт-идентичных блобов. На различном содержимом
экономия ноль во всех проверенных формах, а 10-26 ms (до 61 ms на 2 MB) платятся
всё равно. Для кода это ноль **по замыслу** (`KindCode` — never-touch, пасс 3 в
`distillText`), то есть заведомо известно, что работа не окупится, и она всё
равно выполняется. Единственный ранний выход (`internal/engine/engine.go:98-105`)
— `len(body) < 256` либо отсутствие подстрок `tool`, тройного бэктика и
`diff --git`; в агентском запросе слово `tool` есть всегда. Вызывающая сторона
(2papi) ограничить эту работу не может никак: публичный API — только
`NewEngine(memoCapacity)` и `Apply(body)`.

**Д2 — табличный лифтинг не достаёт до конверта.** `tryTabularLifting`
(`internal/distill/json_tabular.go:139-140`) ищет вложенный массив **только под
четырьмя именами**: `items`, `data`, `results`, `records`. Контрольный прогон —
73 идентичные строки, различается лишь имя ключа обёртки:

| Форма | Лифтинг | Экономия |
|---|---|---|
| массив на верхнем уровне | да | 69.3% |
| обёртка `data` | да | 69.0% |
| обёртка `items` | да | 69.0% |
| обёртка `results` | да | 69.0% |
| обёртка `records` | да | 69.0% |
| обёртка `rows` | **нет** | **0.0%** |
| `matches` / `files` / `entries` / `hits` | **нет** | **0.0%** |
| `diagnostics` / `logs` / `choices` / `content` / `list` | **нет** | **0.0%** |

Разница между 69% и 0% — семь байт имени ключа. Собственная нагрузка бенчмарка
2papi (`test/bench.mjs`, `toolChunk`) использует именно `rows` — поэтому матрица
режимов и показывает, что squoze на профиле `huge` платит за полный проход и не
экономит ничего.

Второй порог, `tabularMinSavings = 0.35`, отбраковывает лифтинг, когда в строках
длинные различающиеся значения (таблица не становится на 35% меньше). Это
**корректное** поведение, и в этой спеке оно не меняется.

## Функциональные требования

### FR-1: Публичный контракт границ работы
- squoze SHALL экспортировать `Limits{MaxBodyBytes, MaxBlockBytes, MinBlockBytes int}`
  и конструктор `NewEngineWithLimits(memoCapacity int, lim Limits) *Engine`.
- WHEN все поля `Limits` нулевые, THEN движок SHALL вести себя как v0.3.0.
- WHEN `MaxBodyBytes > 0` и `len(body) > MaxBodyBytes`, THEN `Apply` SHALL вернуть
  тело без изменений, не выполняя ни `json.Unmarshal`, ни обход `messages`.
- `Result` SHALL получить поля `Skipped bool` и `SkipReason string`
  (`body_too_large` | `no_candidate` | `too_small` | пустая строка).
- Приоритет: MUST
- Критерии приёмки:
  - **AC-1.1**: на всём корпусе `test/squozebench` выход
    `NewEngineWithLimits(cap, Limits{})` побайтно равен выходу `NewEngine(cap)`.
  - **AC-1.2**: при превышении `MaxBodyBytes` — `Skipped=true`,
    `SkipReason="body_too_large"`, выход идентичен входу, `BlocksSqueezed=0`.
  - **AC-1.3**: `NewEngine` и `Apply` сохраняют сигнатуры; сборка 2papi на пине
    v0.4.0 проходит без правок существующих вызовов.

### FR-2: Структурный предпроход, не меняющий выход
- Перед дорогими пассами движок SHALL проверять каждый блок дешёвым структурным
  тестом и пропускать блок, если ни один пасс не может его принять: нет маркеров
  диффа, нет JSON-массива объектов, нет ANSI/CR и классификатор не сказал
  log/test, и блок не является кросс-турновым дублем.
- Приоритет: MUST
- Критерии приёмки:
  - **AC-2.1** (главный): для каждого кейса корпуса выход **с** предпроходом
    побайтно равен выходу **без** него. Гейт снимает только работу, не экономию.
  - **AC-2.2**: на четырёх формах «различное содержимое» из таблицы выше время
    `Apply` падает не менее чем на 50%.
  - **AC-2.3**: кейс с байт-идентичными блобами сохраняет экономию (>=96%) и
    число сжатых блоков.

### FR-3: Досягаемость табличного лифтинга до реальных конвертов
- Массив для лифтинга SHALL находиться структурно, а не по имени: наибольший
  массив из >=3 объектов на глубине <=2, детерминированный тайбрейк — первый в
  порядке документа на наименьшей глубине.
- Раскрытие конверта (`scalarSiblings`) SHALL работать для найденного пути, а не
  только для корня.
- Приоритет: MUST
- Критерии приёмки:
  - **AC-3.1**: контрольная таблица выше становится однородной — идентичные
    строки под любым именем обёртки дают одинаковую экономию.
  - **AC-3.2**: поля конверта не исчезают; `TestJSONEnvelopeLoss`
    (`test/squozebench/verify_test.go:69`) остаётся зелёным.
  - **AC-3.3**: 12 свежих движков дают побайтно равный выход;
    `TestJSONTabularDeterminism` остаётся зелёным.
  - **AC-3.4**: порог `tabularMinSavings = 0.35` не меняется — лифтинг
    по-прежнему отклоняется, когда таблица не даёт материальной экономии.

### FR-4: Видимость пропуска в шлюзе
- 2papi SHALL прокидывать `Result.Skipped/SkipReason` в заголовок
  `X-Gateway-Squoze-Skip` и в телеметрию рядом с существующими
  `X-Gateway-Squoze-*` (`internal/proxy/proxy.go:270-288`).
- Конфигурация: `squoze_max_body_bytes` на уровнях global/model/virtual плюс
  заголовок запроса `X-Gateway-Squoze-Max-Body`.
- Приоритет: MUST
- Критерии приёмки:
  - **AC-4.1**: заголовок присутствует только когда проход пропущен, и несёт причину.
  - **AC-4.2**: значение по умолчанию 0 — поведение шлюза не меняется.

### FR-5: Релиз squoze v0.4.0 и подъём пина
- `engine.Version`, CHANGELOG, тег `v0.4.0`, `go.mod` 2papi поднят на него,
  `replace` на локальный каталог не появляется.
- Приоритет: MUST
- **AC-5.1**: `go build ./...` и `go test ./...` в 2papi зелёные на чистом клоне.

### FR-6: Пересчёт опубликованных чисел
- Приоритет: MUST
- **AC-6.1**: строки squoze в `docs/benchmarks.md` пересняты на v0.4.0, с командой перезапуска.
- **AC-6.2**: `BASELINE` в `test/matrix_compare.mjs:32-46` обновлён — значение
  `squoze (exclusive): 438.56` устарело на два релиза и сейчас пометило бы
  корректный прогон как дрейф.
- **AC-6.3**: строка squozebench в `test/results/README.md` называет актуальную версию.

## Нефункциональные требования

### NFR-1: Детерминизм решения
Ни одно ограничение SHALL NOT зависеть от wall-clock. Дедлайн по времени
запрещён: одинаковые байты обязаны давать одинаковый выход, иначе рушится
prompt-cache провайдера и контракт cache-safety.

### NFR-2: Zero-dep
Никаких новых зависимостей в squoze. ML-подходы вне области (гэп G8 в
`docs/UNFINISHED.md`).

### NFR-3: Стоимость самого предпрохода
Не более 1 ms на теле 2 MB.

### NFR-4: Обратная совместимость
Расширение `Result` полями и добавление конструктора — аддитивные изменения;
существующие вызовы компилируются без правок.

## Edge cases

- Тело больше `MaxBodyBytes`, но целиком состоящее из дублей: экономия теряется.
  Осознанный обмен, поэтому кап по умолчанию выключен (0).
- Массив объектов с более чем 12 колонками — лифтинг отклоняется (существующее правило).
- Массивы глубже двух уровней не лифтятся: документируется как граница, не дефект.
- Блок ровно на границе `MinBlockBytes` — сравнение строгое, чтобы решение не
  зависело от порядка обхода.
- SSE и стриминг не затронуты: `Apply` работает на стороне запроса.

## Ограничения

- Zero-value `Limits` менять поведение не имеет права — на этом стоит AC-1.1.
- Порог 35% не трогаем: это защита от лифтинга, который не экономит.
- Копирование LLMLingua запрещено (ломает zero-dep).
